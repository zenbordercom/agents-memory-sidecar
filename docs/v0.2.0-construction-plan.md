# v0.2.0 Construction Plan

Status: released
Date: 2026-07-06
Target release: v0.2.0

## Goal

Move Agents Memory Sidecar from a working open-source release to a project that
new users can install, validate, and connect to a real agent without relying on
project-specific knowledge.

The target user experience is:

```text
5 minutes: run the demo path and verify the MCP/HTTP memory flow.
30 minutes: run a durable local PostgreSQL deployment.
1 agent: connect a primary agent client to shared memory with a documented flow.
```

This release should not turn the project into a hosted service, dashboard, agent
orchestrator, or broad platform. v0.2.0 should make the existing local-first
sidecar easier to trust and easier to operate.

## Principles

- Keep the project local-first and MCP-first.
- Prefer a complete first-run path over adding new surface area.
- Make PostgreSQL and semantic search usable through documented commands.
- Treat security defaults as part of the product, not an optional production
  appendix.
- Make release validation repeatable.

## Phase 1: First-Run Experience

Improve the path from repository checkout to a successful local smoke test.

Deliverables:

- Restructure the README quick start into clear modes:
  - demo mode with fake store
  - local HTTP sidecar mode
  - durable PostgreSQL mode
- Add or strengthen a single diagnostic entry point, either:
  - `agents-memory doctor`
  - or an expanded `scripts/check-installation.mjs`
- Document token creation for local development without writing secrets to Git.
- Clarify the expected CLI entry points:
  - `agents-memory`
  - `agents-memory-mcp`
  - `agents-memory-http`

Acceptance:

```bash
npm install
npm run build
npm run smoke
npm run http:smoke
```

A new user should be able to run those commands without understanding the full
architecture first.

## Phase 2: PostgreSQL Durable Deployment

Make the durable local deployment path explicit and repeatable.

Deliverables:

- Add `docs/postgres-quickstart.md`.
- Document database creation, application role creation, pgvector setup,
  migrations, HTTP startup, memory write, memory search, and memory read.
- Make `npm run postgres:smoke` the required validation path for PostgreSQL
  changes.
- Keep the default open-source layout consistent:
  - config: `/etc/agents-memory`
  - runtime: `/opt/agents-memory-sidecar`
  - backups: `/var/backups/agents-memory`

Acceptance:

```bash
AGENT_MEMORY_BACKEND=postgres npm run db:migrate
npm run postgres:smoke
```

The durable deployment path should work on a clean local PostgreSQL environment
after the documented setup steps are complete.

## Phase 3: Semantic And Hybrid Search

Turn the existing pgvector search support into a practical workflow.

Deliverables:

- Document Ollama as the first supported embedding path.
- Standardize the initial model example on `nomic-embed-text`.
- Document:
  - readiness checks
  - dry-run backfill
  - write backfill
  - switching `AGENT_MEMORY_SEARCH_MODE`
  - fallback behavior when embeddings are unavailable
- Add `docs/semantic-search.md`.
- Confirm that semantic and hybrid search return clear metadata such as
  `search_mode`, `embedding_model`, and score fields.

Acceptance:

```text
memory_items > 0
memory_embeddings > 0
AGENT_MEMORY_SEARCH_MODE=hybrid
memory_search returns search_mode=hybrid
```

## Phase 4: Primary Agent Integration

Make one primary agent integration excellent before expanding every client path.

The recommended first target is Codex because the project is aimed at coding
agents and Codex is a direct fit for the core workflow.

Deliverables:

- Expand the Codex integration guide with:
  - token env file
  - launcher script
  - MCP configuration
  - validation command
  - common failure modes
- Document the recommended memory workflow:
  - call `project_context_get` at the start of project work
  - call `memory_search` before changing a project
  - call `memory_add` only after an important fact is validated
  - use `agent_observation_add` for temporary process notes
- Add a small demo flow that writes context, searches memory, reads one item,
  and adds a new memory.

Acceptance:

```text
Codex can call memory_search, memory_add, and project_context_get through MCP.
```

## Phase 5: Release Engineering

Make v0.2.0 repeatable to build, verify, package, and publish.

Deliverables:

- Ensure CI covers:
  - typecheck
  - fake store smoke
  - HTTP smoke
  - PostgreSQL + pgvector smoke
  - package build
- Add a release checklist covering:
  - changelog update
  - version bump
  - `npm pack`
  - local smoke tests
  - PostgreSQL smoke tests
  - Git tag
  - GitHub release artifact
- Keep README project boundaries visible:
  - local-first sidecar
  - not a hosted SaaS API
  - not an agent scheduler
  - not a secret manager
  - not full conversation memory

Acceptance:

```text
v0.2.0 can be released by following the checklist without hidden local steps.
```

## Deferred

These are intentionally outside the first v0.2.0 construction pass:

- Web dashboard or UI
- Public multi-tenant API
- Agent orchestration
- IM or Telegram health notifications
- Deep integration for every agent runtime
- Complex memory governance workflows
- Remote hosted deployment model

## Exit Criteria

v0.2.0 is ready when:

- A new user can run the fake-store demo without external services.
- A new user can follow a PostgreSQL quickstart to durable memory.
- Hybrid search has a documented, verified embedding path.
- Codex has a complete MCP integration guide.
- Release validation is repeatable from documented commands.
- Public docs do not expose secrets or private deployment assumptions.
