# v0.3.0 Construction Plan

Status: planned
Date: 2026-07-17
Target release: v0.3.0

## Goal

Move Agents Memory Sidecar from a validated local-first MVP to a trustworthy
open-source component that fails closed, has a complete distribution path, and
can be installed and tested by users who do not know the repository internals.

The target user experience is:

```text
1 command: install the current package from npm and verify all CLI entry points.
Fail closed: starting the HTTP sidecar without an explicit auth configuration is rejected.
1 workflow: start a durable PostgreSQL + pgvector deployment with repeatable commands.
1 report: measure keyword, semantic, and hybrid search behavior against a fixed fixture set.
```

v0.3.0 is a hardening and adoption release. It should improve trust in the
existing architecture before adding broad new product surfaces.

## Baseline

At the start of this plan:

- GitHub releases `v0.1.0` through `v0.2.1` exist.
- The `v0.2.0` construction plan is complete.
- The repository version and GitHub latest release are `0.2.1`.
- The npm registry `latest` tag still points to `0.1.1`.
- CI covers typecheck, build, fake-store smoke, HTTP smoke, MCP-over-HTTP smoke,
  migration, and PostgreSQL + pgvector smoke on Node.js 24.
- Production dependency audit reports no known vulnerabilities.
- GitHub does not recognize the abbreviated `LICENSE` file as Apache-2.0.
- HTTP requests fall back to the environment actor when no token registry is
  configured, which makes authentication fail open.
- The repository has smoke programs but no dedicated unit-test suite, coverage
  threshold, or supported-Node test matrix.
- External adoption has not produced enough issues, pull requests, stars, or
  forks to validate the onboarding experience.

## Principles

- Keep the project local-first and MCP-first.
- Fail closed at security boundaries; require explicit opt-in for insecure demo
  behavior.
- Complete release and installation paths before expanding features.
- Convert important security and data-isolation claims into automated tests.
- Prefer deterministic fixtures and measurable search behavior over subjective
  examples.
- Keep deployment automation inspectable and suitable for local ownership.
- Preserve backward compatibility unless retaining it would keep an unsafe
  default.

## Scope

v0.3.0 includes:

- Closing the `v0.2.1` npm and license publication gaps.
- Fail-closed HTTP authentication and safer error responses.
- Unit and integration test foundations with a supported Node.js matrix.
- Automated, verifiable npm release engineering.
- A repeatable PostgreSQL + pgvector local deployment workflow.
- Initial search-quality fixtures and memory-governance documentation.
- Open-source contribution and security-reporting improvements.

## Non-Goals

The following remain outside v0.3.0:

- Hosted SaaS or a public multi-tenant API
- Web dashboard or administration UI
- Agent scheduling or orchestration
- Full conversation capture or replay
- Secret storage or complete DLP
- Remote embedding services enabled by default
- Deep integrations for every agent runtime
- A stable public API guarantee beyond the documented MCP and HTTP v1 surfaces

## Phase 0: Close The v0.2.1 Release

Finish the release that is already present on GitHub before changing runtime
behavior.

Deliverables:

- Publish `agents-memory-sidecar@0.2.1` to npm with the `latest` dist-tag.
- Install `0.2.1` from npm in a clean temporary project and verify all three CLI
  entry points.
- Replace the abbreviated license with the complete Apache License 2.0 text and
  identify the copyright holder.
- Confirm GitHub recognizes the repository license as Apache-2.0.
- Update installation documentation so GitHub and npm release guidance no
  longer contradict each other.
- Record release verification evidence without storing credentials or tokens.

Acceptance:

```text
npm view agents-memory-sidecar version returns 0.2.1
npm view agents-memory-sidecar dist-tags.latest returns 0.2.1
a clean npm install exposes agents-memory, agents-memory-mcp, and agents-memory-http
GitHub reports the repository license as Apache-2.0
```

## Phase 1: Fail-Closed HTTP Security

Make bearer authentication an enforced HTTP boundary instead of a documentation
convention.

Deliverables:

- Refuse to start the HTTP sidecar when neither a token registry nor an explicit
  local unauthenticated opt-in is configured.
- Add `AGENT_MEMORY_ALLOW_UNAUTHENTICATED_LOCAL=1` for deliberate demo and test
  use only.
- Require unauthenticated mode to bind to a loopback address.
- Validate token registry JSON and actor records at startup with actionable,
  secret-safe errors.
- Keep `/healthz` behavior explicit and document whether it requires auth.
- Return stable public error codes for HTTP 500 responses while logging a
  request ID and sanitized internal detail server-side.
- Handle `SIGINT` and `SIGTERM` by stopping the listener and closing the store.
- Update configuration, security, quickstart, systemd, and troubleshooting docs.

Acceptance:

```text
HTTP startup without auth configuration fails
explicit unauthenticated loopback demo mode starts
unauthenticated non-loopback startup fails
missing, malformed, and unauthorized tokens return expected status codes
internal database or embedding errors are not returned verbatim to clients
```

## Phase 2: Test Foundation And Compatibility

Turn critical behavioral claims into focused automated tests while retaining the
existing end-to-end smoke coverage.

Deliverables:

- Select and configure a test runner compatible with the current TypeScript and
  ESM setup.
- Add unit tests for actor authorization, project scoping, input validation,
  secret rejection, duplicate detection, and search-mode validation.
- Add HTTP integration tests for authentication, role permissions, tenant and
  project isolation, malformed JSON, body limits, error sanitization, and
  graceful shutdown.
- Add PostgreSQL integration tests for migrations, duplicate writes, TTL
  pruning, keyword search, semantic search, and hybrid fallback.
- Add a coverage report and define an initial threshold for security-critical
  modules.
- Declare the supported Node.js range in `package.json`.
- Run CI against the minimum supported Node.js version and the current release
  line; keep the PostgreSQL job on one canonical Node.js version.
- Add `npm test` as the contributor-facing validation command.

Acceptance:

```text
npm test passes from a clean checkout
CI covers every declared supported Node.js release line
authorization and isolation failures have regression tests
PostgreSQL migrations and search modes pass in CI
coverage cannot regress below the documented threshold
```

## Phase 3: Release And Supply-Chain Engineering

Make version publication reproducible and prevent GitHub/npm release drift.

Deliverables:

- Add an automated release workflow triggered by a protected version tag or a
  manually approved GitHub environment.
- Verify that `package.json`, the Git tag, changelog, and intended npm version
  agree before publication.
- Use npm trusted publishing when the repository and npm organization support
  it; otherwise document the minimum-scope token fallback.
- Publish npm provenance and retain package integrity metadata in the GitHub
  Release notes.
- Run package-content, clean-install, CLI, and smoke verification before
  publication.
- Verify the npm dist-tag and clean registry installation after publication.
- Prevent republishing an existing version and prevent moving `latest`
  accidentally during prereleases.
- Update the release checklist to distinguish release-candidate, stable, and
  hotfix paths.

Acceptance:

```text
one approved workflow publishes matching GitHub and npm releases
tag, package version, changelog, and dist-tag mismatch causes a hard failure
the published package includes provenance and passes clean-install verification
no undocumented local release step is required
```

## Phase 4: Repeatable Durable Deployment

Reduce the durable setup path from a long manual transcript to an inspectable,
repeatable workflow.

Deliverables:

- Add a Docker Compose example for PostgreSQL + pgvector and the sidecar, or
  document a rejected alternative if packaging constraints make Compose unsafe.
- Keep the HTTP port bound to loopback by default.
- Generate local development tokens without printing full values to terminal
  output.
- Add health checks and startup dependency ordering.
- Run migrations explicitly and make migration failure visible.
- Persist PostgreSQL data in a named local volume and document removal and
  backup implications.
- Add a clean-start and restart-persistence smoke test.
- Keep the existing native PostgreSQL and systemd paths supported and
  documented.

Acceptance:

```text
a new user can start a durable local deployment with documented commands
the deployment survives a normal restart with memories intact
HTTP remains loopback-only by default
health, auth, migration, write, search, and read checks pass
```

## Phase 5: Search Quality And Memory Governance

Establish measurable behavior before adding more retrieval providers or memory
management tools.

Deliverables:

- Add a small, versioned, non-sensitive search fixture set with expected query
  relevance judgments.
- Add a benchmark command that reports keyword, semantic, and hybrid result
  quality and latency without claiming statistical significance.
- Record embedding model, dimensions, search mode, and fallback behavior in the
  report.
- Document canonical project naming and namespace conventions.
- Document the lifecycle for duplicate rejection, summary correction, soft
  deletion, observation expiry, and audit review.
- Decide whether the existing maintenance scripts remain operator-only or need
  a documented admin API in a later release.
- Define an embedding-provider interface proposal, but implement additional
  providers only if a real integration requires them.

Acceptance:

```text
the benchmark is deterministic enough to detect obvious retrieval regressions
fallback from semantic or hybrid mode is visible in results
operators have a documented memory correction and deletion workflow
v0.3.0 does not silently expand the admin attack surface
```

## Phase 6: Open-Source Readiness

Make it easier for external users to report problems and contribute without
requiring private project knowledge.

Deliverables:

- Expand `CONTRIBUTING.md` with environment requirements, test commands, change
  scope guidance, and pull-request expectations.
- Add a usable private security-reporting contact or GitHub private
  vulnerability reporting instructions.
- Add issue templates for bugs and installation problems.
- Add a pull-request template with validation and secret-safety checks.
- Add a support matrix for operating systems, Node.js, PostgreSQL, pgvector, and
  tested agent clients.
- Create a small set of bounded `good first issue` candidates only after the
  corresponding maintainer workflow exists.
- Run at least one clean-room onboarding rehearsal that follows only public
  documentation and record the resulting fixes.

Acceptance:

```text
an external contributor can identify prerequisites and required checks
security reporters have a concrete private reporting path
installation reports collect enough version and environment data to reproduce failures
a clean-room user completes the documented demo without repository-specific help
```

## Execution Order And Gates

Work should proceed in this order:

1. Phase 0 closes the existing release gap.
2. Phase 1 changes the security contract and must land before deployment
   automation.
3. Phase 2 locks the new contract into tests.
4. Phase 3 automates release only after the test and security gates are stable.
5. Phases 4 and 5 may proceed in parallel after Phase 2 if their write scopes do
   not overlap.
6. Phase 6 runs throughout the release, with the clean-room rehearsal as the
   final pre-release gate.

Every phase requires:

- implementation and focused tests
- documentation and configuration examples
- a clean package-content check
- review for secret exposure and private deployment assumptions
- an independent review for security-sensitive or release-sensitive changes

## Exit Criteria

v0.3.0 is ready when:

- npm and GitHub expose the same current stable release.
- GitHub recognizes the project as Apache-2.0 licensed.
- HTTP authentication fails closed unless explicit loopback demo mode is enabled.
- Security-critical authorization and isolation behavior has regression tests.
- CI covers the declared Node.js support range and PostgreSQL + pgvector.
- A clean user can start and validate a durable local deployment using only
  public documentation.
- Search behavior has a repeatable fixture-based baseline.
- Release publication is approved, reproducible, and verified after publish.
- Security reporting and contribution paths are concrete.
- Independent review finds no unresolved P0 or P1 release blocker.

## Release Decision

The release candidate can be tagged only after all P0 and P1 tasks are complete.
P2 tasks may be deferred only through an explicit documented decision that does
not weaken the exit criteria. Any failure in authentication isolation, package
installation, migration, or release-version consistency blocks the release.
